Glossary (compact)

Entropy / packing
High byte randomness (often >7.0) hints a file may be compressed/encrypted/packed — a lead, not proof of malware.
imphash
Hash of the PE import table order/names; similar imphash → same toolchain/family candidate for pivoting.
ssdeep
Fuzzy hash; near-matches help cluster variants that changed a few bytes.
Imports
APIs the PE claims to call (network, crypto, process). Odd imports for the claimed app type are hunt leads.
PE / MZ
Windows executable format; bytes 4D 5A (“MZ”) mark the DOS stub of a PE image in file or memory.
Process-tree lineage
Parent→child chain (e.g. WINWORD→cmd). Impossible parents are strong exam IOCs.
Triage
Selective copy of high-value artifacts — not a full disk image.
collection_context / log.json
Manifests that record what a collector grabbed, when, and from which host/path.
Dirty hive + .LOG1/.LOG2
Registry hive copied while OS was live; transaction logs must be collected with the hive to replay consistency.
DCSync
Abuse of directory replication APIs to pull credential material; contrast with expected DC↔DC replication.
krbtgt
Domain KRBTGT account; after suspected ticket abuse, rotate twice so old and intermediate keys both die.
Event 4104
PowerShell script-block logging; absent when the dump tool is a native EXE (no PS engine).
4688 / Sysmon 1
Process-create events that carry command-line — primary hunt surface for native dump-tool IOC strings.
Layered persistence
Multiple independent footholds; remove one and others remain.
Mutually restoring
Mechanisms that reinstall each other; need a coordinated removal window.
PID 4 boot time
System process create time ≈ last boot; windows.info alone does not give boot time.
ProfileList vs sessions
Historical logons vs who was logged in at capture time.
pslist / psscan / pstree
Active list vs pool scan (hidden/exited, DKOM unlink) vs parent/child tree.
DKOM unlink
Kernel-object manipulation that unlinks a process from the active list so pslist misses it.
getsids / S-1-5-18
Process token SIDs; S-1-5-18 = local SYSTEM.
malfind
Finds private RWX regions; RWX+MZ in an odd process = lead (JIT can FP).
modules vs driverscan
Loaded images vs driver objects — compare by address, not name/count.
vadinfo private vs file-backed
Private = no file mapping; both hollowing and reflective load look private.
Injection / hollowing / reflective / side-load
Different memory/disk patterns — do not conflate with DLL search-order side-load.
malfind --dump vs dumpfiles
Carve private injected regions vs extract file-backed images from memory.
NTFS 0x10 vs 0x30
STANDARD_INFORMATION vs FILE_NAME timestamps; SI/FN mismatch is a timestomp lead.
MFTECmd
Eric Zimmerman parser for $MFT / USN timelines and 0x10 vs 0x30 checks.

A Static / sandbox commands & PE

01 — What each command does

What it means — Basic static triage: make a work folder, record SHA-256 (and keep a copy via tee), identify file type, note size.

Why it matters on exam — Exams expect a safe order: hash first so every later note ties to one sample identity.

Example — You see sha256sum sample.exe | tee hash.txt then file sample.exe reporting “PE32 executable” — you write the hash into the report header before sandboxing.

02 — The report’s static panel

What it means — Entropy measures randomness (packing/encryption hint). imphash fingerprints the import table. ssdeep fuzzy-matches near-duplicates. Imports list claimed APIs.

Why it matters on exam — Questions often ask what each field is for — and that high entropy alone ≠ malware.

Example — Panel shows entropy 7.4, imphash matching a known packer family sample, imports including WinHttpOpen in a “calculator” binary — hunt/cluster lead, not a conviction.

03 — PE/MZ + process-tree lineage

What it means — PE files start with MZ (4D 5A). Lineage is who spawned whom in sandbox or EDR trees.

Why it matters on exam — Spot impossible parents: Office spawning cmd/powershell is a classic Day-1 IOC pattern.

Example — Sandbox tree: WINWORD.EXE → cmd.exe → encoded PowerShell — you flag the lineage and the child cmdline as evidence of macro-driven execution, not “Word is malware.”

04 — MITRE ATT&CK Day-1 subset

What it means — A short technique list covering initial access → execution → persistence you’ll map evidence to on exam day.

Why it matters on exam — Map artifacts to technique IDs (e.g. scheduled task ↔ T1053.005) without inventing attacker steps.

Example — Phish macro + Run key + scheduled task → cite T1566.001, T1547.001, T1053.005 with the Event IDs / paths that prove each.

B Triage & artifacts

05 — Triage = selective copy

What it means — Triage grabs high-value paths (hive, EVTX, MFT, Prefetch…), not a full disk. collection_context and log.json document what landed.

Why it matters on exam — Know triage ≠ imaging; exam answers often hinge on reading the manifest for gaps.

Example — Manifest lists SOFTWARE hive but not SYSTEM — you note incomplete collection before concluding “no service persistence.”

06 — Artifact category → path

What it means — Cheat map from evidence type to default Windows path under a triage root.

Why it matters on exam — Speed: “Where is Amcache / Prefetch / Tasks?” is pure path recall.

Example — Asked for program execution evidence → Prefetch + Amcache paths; asked for WMI persistence → permanent event subscription store under WBEM.

07 — Dirty SOFTWARE hive

What it means — A hive copied while Windows was running is dirty until transaction logs (.LOG1/.LOG2) are replayed with a forensic parser.

Why it matters on exam — Correct answer is almost always: collect hive and logs — orphan hive alone may miss recent keys.

Example — Quiz: live SOFTWARE without logs → incomplete; with hive + LOG1/LOG2 → parsers can reconcile dirty writes.

C Cred dump / DCSync / IR response

Detection framing

Credential-access tooling below is listed only as what Security/Sysmon show and what to hunt. Treat suspicious dump-tool command lines as IOC strings (e.g. process name + path + target process), not procedures to run.

08 — DCSync vs legitimate replication

What it means — Directory replication APIs used by DCs are also abused to pull secrets (DCSync). Legitimate traffic is DC↔DC; suspicious is non-DC / unexpected subject pulling replication rights.

Why it matters on exam — Distinguish 4662 noise from “non-DC subject + replication GUIDs + odd 4624 source.”

Example — Hunt: Security 4662 with replication GUIDs where Subject is a workstation admin account, not a DC computer account — escalate as DCSync-class activity.

09 — No 4104 when dump is a native EXE

What it means — PowerShell script-block logging (4104) only sees script. A native dump EXE never enters the PS engine, so 4104 stays quiet.

Why it matters on exam — Pivot to process-create cmdline (4688 / Sysmon 1) for IOC strings naming dump tools and LSASS as target — detection patterns only.

Example — Exam trap: “No 4104 ⇒ no cred dump” is false. You hunt 4688/Sysmon 1 for process image + command-line tokens consistent with LSASS access tools.

10 — DCSync impact & remediation

What it means — If domain secrets were pulled, assume credential material is burned; remediation includes widespread password resets and KRBTGT rotation.

Why it matters on exam — Remember krbtgt ×2: one rotation leaves a previous key valid for ticket forgery windows.

Example — Answer key: isolate, reset passwords domain-wide as scoped by IR plan, rotate krbtgt twice, hunt Golden Ticket return paths.

11 — Domain compromise IR

What it means — IR play: contain AD trust boundary, find how they return (persistence + identities), then key rotation.

Why it matters on exam — Order matters: contain → evidence → eradicate persistence → reset/rotate.

Example — Scenario answer: take affected DCs offline from untrusted segments, preserve logs/memory, hunt persistence, then krbtgt×2 after footholds are gone.

D Persistence

12 — Layered persistence

What it means — Several independent mechanisms (Run key + service + task + WMI…). Removing one leaves others.

Why it matters on exam — Exam: “list all then remove” — incomplete lists fail cleanup questions.

Example — You document four footholds across Autoruns categories, confirm each with path+cmdline+time+account, then plan removal of all four.

13 — Mutually restoring persistence

What it means — Mechanism A reinstalls B and B reinstalls A (or a watcher repairs both).

Why it matters on exam — Need a coordinated window (or offline image) so both die together.

Example — Task recreates a service binary and the service recreates the task — remove both in one change window while host is isolated.

E Memory forensics / Volatility

14 — Boot time + ProfileList vs sessions

windows.info does not report when the machine last booted. The System process (PID 4) is created at boot and runs until shutdown, so its creation time is the boot time.

vol -f <memory.raw> windows.info
vol -f <memory.raw> windows.pslist

Use pslist (or pstree) to read PID 4 / System create time.

ProfileList vs windows.sessions

They do not answer the same question:

Plugin / keyAnswers
ProfileList (HKLM\...\ProfileList)Every account that has ever logged in — historical record
windows.sessionsWho was logged in at the moment of capture
 
vol -f <memory.raw> windows.registry.hivelist
vol -f <memory.raw> windows.registry.printkey \
  --key "Microsoft\Windows NT\CurrentVersion\ProfileList"
vol -f <memory.raw> windows.sessions
vol -f <memory.raw> windows.pstree

What it means — Boot time ≈ PID 4 create time. ProfileList = historical profiles; sessions = live at dump time.

Why it matters on exam — Trick questions swap “ever logged in” with “logged in now.”

Example — ProfileList shows alice + bob; sessions shows only alice → bob is historical, not present at capture.

15 — pslist vs psscan vs pstree

PluginWhat it does
windows.pslistWalks the active process list the way the OS does. Fast and accurate for anything running normally.
windows.psscanScans raw memory for process structures instead of trusting the list. Finds processes that have exited, and processes deliberately unlinked from the list to hide them.
windows.pstreeShows the same processes as a parent/child tree. Most problems show up here, because malware often has a parent process that makes no sense.

Exam tip: pslist ≠ psscan → look for hidden or exited processes (including DKOM-style unlink). Use pstree to spot impossible lineages.

What it means — DKOM unlink = process still in memory but removed from the active list so pslist misses it; psscan can still find the EPROCESS.

Why it matters on exam — Diff the two lists; then use pstree for “weird parent.”

Example — psscan shows malware.exe PID 4242 absent from pslist → suspect unlink/hide; confirm with handles/netscan on that PID.

16 — cmdline, dlllist, getsids, handles

PluginWhat it showsWhy it matters
windows.cmdlineFull command line each process was launched withEncoded or obfuscated arguments are a strong indicator
windows.dlllistModules (DLLs) each process has loadedA networking DLL inside a process that has no reason to talk to the network is a well-known indicator
windows.getsidsSecurity identifiers (SIDs) a process holds — whose authority it runs underA normally unprivileged program running as SYSTEM means privilege escalation happened. SID S-1-5-18 is the built-in SYSTEM account (highest local privilege)
windows.handlesOpen objects a process holds: files, registry keys, named pipesPipes are one way separate malware components talk to each other on the same host

What it means — Four “enrichment” plugins: args, modules, token SIDs, open objects (incl. named pipes).

Why it matters on exam — S-1-5-18 on a user app = priv-esc lead; odd wininet/winhttp in notepad-like process = C2 lead.

Example — getsids shows notepad as S-1-5-18; handles shows a suspicious named pipe between two PIDs — document both as hunt findings.

17 — netscan + malfind

windows.netscan

Recovers TCP and UDP endpoints, including sockets already closed by capture time. Shows local/remote address, port, connection state, and owning PID.

windows.malware.malfind

Flags memory that is executable and writable but backed by no file on disk. That combination is the signature of injected or reflectively-loaded code. The plugin prints a hexdump of the first bytes so you can see whether they begin 4D 5A (MZ).

False positives

Some legitimate software allocates RWX memory genuinely — anything with a JIT compiler (browsers, .NET runtime).

Interesting hit = RWX and MZ header and a process that has no reason to be doing it.

Treat malfind as leads to check, not conclusions to report.

What it means — netscan = sockets (incl. closed). malfind = private RWX; MZ at start strengthens the lead; JIT = common FP.

Why it matters on exam — Never report “malware” from RWX alone — require context (process + MZ + behavior).

Example — RWX+MZ inside spoolsv.exe with netscan showing rare remote IP → escalate; RWX in chrome.exe without MZ → likely JIT, deprioritize.

18 — windows.modules vs windows.driverscan

These plugins do not report the same kind of thing.

PluginWhat it walksHow things are named
windows.modulesKernel’s list of loaded module imagesAs files — ntoskrnl.exe, hal.dll, Path under \SystemRoot\system32\
windows.driverscanMemory for driver objectsIn the device namespace — \Driver\HTTP, \Driver\00000311

One image can own several driver objects, and scanning finds the same object more than once.

What does / does not prove

  • Comparing the two counts proves nothing — they count different kinds of thing.
  • Comparing the two name lists proves nothing — ntoskrnl.exe and \Driver\HTTP are not in the same namespace; no name will match.

The comparison that means something

Map by address: take each driver object’s Start from driverscan and find the module in modules whose Base … Base+Size range contains it.

A driver object whose Start falls inside no loaded module is worth investigating — something is executing in kernel space that the module list does not account for.

Lab scope note: full address mapping may be beyond a day’s exercise; still run both, record counts, and state clearly what the check does and does not support.

What it means — modules = file-named images; driverscan = \Driver\ objects. Meaningful join is by address range.

Why it matters on exam — Exam trap: “counts differ ⇒ rootkit” is wrong; “orphan Start address” is the real signal.

Example — Driver Start 0xFFFFF80001234000 not inside any modules Base..Base+Size → investigate unaccounted kernel code.

19 — What modules/driverscan showed

What it means — Getting a listing only proves you ran the plugins — not that the host is clean.

Why it matters on exam — State limitations: without address mapping you cannot claim “no hidden drivers.”

Example — Lab write-up: “Ran modules + driverscan; counts recorded; address map deferred — listing alone ≠ clean.”

20 — vadinfo: hollowing vs reflective

Two columns do the work, not one.

windows.vadinfo lists a process’s memory regions and, for each one, whether it is backed by a file on disk. That separates file-backed code from private code.

It does not separate process hollowing from reflective loading, because both are private. For that you also check whether the main image region is still intact.

Read both before you name a technique.

What it means — Private VAD = not mapped from a file. Hollowing and reflective both present as private; check if the main image VAD is still healthy.

Why it matters on exam — Don’t name “hollowing” from “private” alone.

Example — Private RWX region + intact file-backed main image → lean reflective/injected; main image region replaced/empty while process name looks legit → lean hollowing hypothesis.

21 — Injection vs hollowing vs reflective

What it means — Injection: foreign code into a living process. Hollowing: replace contents of a started process. Reflective: load PE from memory without normal loader. Side-load: drop a DLL where a trusted app will load it from disk search order.

Why it matters on exam — Side-load is a disk/search-order story; the others are primarily memory stories.

Example — File-backed suspicious DLL next to a signed EXE → side-load lead; private MZ in memory with intact main image → reflective/inject lead.

22 — malfind dump vs dumpfiles

What it means — Use malfind --dump to carve private injected regions; use dumpfiles when the image is (or was) file-backed and still referenced in memory.

Why it matters on exam — Wrong plugin = empty or wrong artifact for the question.

Example — Exam: “extract the injected PE with no path on disk” → malfind dump; “recover the DLL still mapped from System32” → dumpfiles.

F NTFS / MFTECmd

23 — NTFS 0x10 vs 0x30 (timestomp lead)

What it means — Attribute 0x10 (STANDARD_INFORMATION / SI) is what Explorer-style stamps often show; 0x30 (FILE_NAME / FN) is updated differently and is harder for simple stomps to keep consistent.

Why it matters on exam — SI≪FN or other mismatches are a timestomp lead, not proof by themselves — correlate with $Us / Prefetch / logs.

Example — SI Created far earlier than FN Created on the same record → flag timestomp lead; confirm with USN and parent folder times.

24 — MFTECmd

Eric Zimmerman MFT parser — used for $MFT / $J (USN) timelines, create/modify/delete, and checking 0x10 vs 0x30 timestamps.

Typical lab path:

C:\Training\Tools\EricZimmerman\MFTECmd.exe

Pairs with: Timeline Explorer, AmcacheParser, Hayabusa.

What it means — Parses MFT/USN into CSV for timeline tools; exposes SI vs FN columns for stomping hunts.

Why it matters on exam — Know which tool answers “0x10 vs 0x30” questions (MFTECmd + Timeline Explorer).

Example — Export $MFT with MFTECmd → open in Timeline Explorer → filter SI/FN mismatches around the incident window.

Quick exam anchors
  • Static order: hash → file → entropy/imphash → imports → sandbox lineage
  • Dirty hive → collect hive and transaction logs
  • Native dump EXE → no PS 4104; hunt 4688 / Sysmon 1 cmdline IOCs
  • DCSync remediation → domain-wide reset + krbtgt ×2
  • pslist ≠ psscan; malfind = leads (RWX+MZ+odd process)
  • modules vs driverscan → map by address, not name/count
  • vadinfo: private vs file-backed; both hollow + reflective are private
  • Timestomp lead: SI (0x10) vs FN (0x30) mismatch

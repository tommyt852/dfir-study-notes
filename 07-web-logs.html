Section 07

Web Logs

Apache/IIS parsing and web shell detection for DFIR

Download PDF · Overview

Learning objectives

  • Parse Apache and IIS W3C fields correctly (especially changing #Fields)
  • Filter logs by URI, status, IP, method, time, and request id
  • Prove web shell execution via request + w3wp child process correlation
  • Avoid the HTTP 200 = success trap

Why web logs matter

Web servers are frequent initial access and persistence points. Logs show who requested what, when, and with which response code — but they do not by themselves prove server-side command execution. Always be ready to join logs to host process evidence.

Apache logs (common / combined)

Typical combined-style fields include: client IP, identity, user, timestamp, request line (method, URI, protocol), status code, size, referrer, User-Agent. Exact format is controlled by the LogFormat directive — confirm the format string in scope.

  • Hunt: rare URIs, .php/.jsp/.aspx under upload dirs, admin panels from odd IPs
  • Status clusters: repeated 404 (scanning), sudden 500 (exploit fail), 200 on unusual paths
  • Methods: unexpected PUT/MOVE/PROPFIND on IIS/WebDAV-enabled servers

IIS W3C logs — critical exam point

IIS W3C extended logs begin with directive lines. The #Fields: header defines column order — and that order can change across servers or after configuration updates. Never hard-code column positions from memory; always read #Fields for the file you are parsing.

Common fieldUse in investigations
c-ip / s-ipClient vs server address
cs-methodGET/POST/etc.
cs-uri-stem / cs-uri-queryPath and query string — web shell params often here
sc-statusHTTP status returned
cs-user-agentScanner vs browser vs automation
cs(Referer)Navigation path / CSRF clues
time / dateAlign with host 4688 — watch time zones
s-port / cs-versionService identification

Filtering strategy

  • Narrow by time window of the alert
  • Filter URI keywords: cmd, whoami, eval, .ashx, unusual upload paths
  • Stack by IP and method; isolate rare combinations
  • Use request id / correlation id if present to join to app traces
  • Export candidates then pivot to the web server host

Web shells — proving execution

Adversaries may upload or write a web shell and invoke it over HTTP. A useful evidence chain on IIS:

  • Request in IIS log to a suspicious ASPX/ASHX/PHP path (often POST)
  • Worker: w3wp.exe (IIS application pool process) handles the request
  • Execution: child processes such as cmd.exe or powershell.exe under w3wp — visible in 4688/Sysmon 1
  • On disk: the shell file itself (hash, MFT create time near first request)
Critical misconception
  • HTTP 200 does NOT prove the attack succeeded — only that the server returned OK.
  • A request in the log does NOT equal command execution.
  • Prove execution with process creation (and preferably command line) tied to the worker process.
  • Conversely, execution might occur even if you have incomplete logs — host evidence still matters.

How do I prove a web shell?

  • Find first successful-looking request to the shell path in W3C/Apache logs
  • On the server: locate file; hash; check write source (WebDAV, upload bug, RCE)
  • Confirm w3wp (or apache/httpd/php-fpm) spawned shell/interpreter processes at that time
  • Trace what commands ran; assess data access; contain (take app offline / remove shell / rotate)

Common exam traps

  • Assuming fixed IIS column order without reading #Fields
  • Equating HTTP 200 with compromise success
  • Ignoring time zone skew between web logs and Windows event logs
  • Hunting only .aspx while shells use .ashx, images with appended payloads, etc.
  • Forgetting that reverse proxies change c-ip (use X-Forwarded-For if logged)

Lab takeaways

From Lab 4-1 — Web attacks / webshell
  • Join WAF ↔ IIS on request ID (d4rid), not nearest timestamp. Blocked probes can legitimately have zero IIS rows.
  • Gateway decode-then-match order can miss encoded probes — missed detection may be a control limit, not "attacker skill".
  • Prove webshell execution: IIS 200 alone insufficient; need w3wp → cmd/powershell 4688 + matching request marker + app exit success (Hayabusa "Suspicious Process By Web Server Process").
  • Watch writable uploads paths for .aspx placement; MFTECmd helps timeline file drop vs first hit.
Quick reference
  • Always parse IIS #Fields — order can change
  • Filter: URI, status, IP, method, time, request id
  • Web shell chain: request → w3wp.exe → cmd/powershell
  • 200 ≠ success; request ≠ execution
  • Join logs to 4688/Sysmon on the web server

Mini self-check

Try answering without looking back. Expand each item for the answer.

Q1. Why must analysts read the IIS #Fields line every time?
A1. Because the field order can change across configurations; hard-coded positions mis-parse the log.
Q2. What process typically hosts ASP.NET request execution on IIS?
A2. w3wp.exe (IIS worker process for the application pool).
Q3. What host evidence proves a web shell ran a command?
A3. Child process creation (e.g., cmd.exe or powershell.exe) under w3wp.exe correlated in time with the request, plus the shell file on disk.
Q4. Why is HTTP 200 insufficient proof of a successful exploit?
A4. It only indicates the HTTP response code was OK; it does not prove malicious server-side execution.
Q5. Name four useful filter dimensions for web log triage.
A5. URI, status, IP, method (also timestamp and request id).

Section 02

Triage & Collection

Velociraptor and KAPE for scalable DFIR acquisition

Download PDF · Overview

Learning objectives

  • Choose Velociraptor vs KAPE for live hunt vs targeted disk triage
  • Explain KAPE Target vs Module and name key collectors/parsers
  • List high-value Windows artifacts to collect first
  • Preserve forensic soundness: order of volatility and documentation

Triage mindset

Triage is not full forensics — it is enough evidence, fast enough to decide containment and next deep-dives. Over-collection wastes time; under-collection loses volatile proof. Prefer: memory (if safe) → critical logs/registry/MFT → broader disk.

Velociraptor

Velociraptor is an open-source endpoint visibility and DFIR platform. For exams, remember four verbs: collect, hunt, live response, artifacts.

CapabilityWhat it meansWhen to use
CollectionPull defined artifact sets from endpoints to the serverKnown IOCs; scoped incident hosts
HuntQuery many endpoints for a condition (file hash, mutex, reg key)Fleet-wide: 'who has this beacon path?'
Live responseInteractive investigation on a live host via VQLHot box where reboot would destroy evidence
ArtifactsReusable VQL packs (Windows.EventLogs, prefetch, etc.)Standardize what juniors collect

Velociraptor shines when you need scale and repeatable hunts. Pair with offline parsers (or export) when deep timeline work is needed on a workstation.

KAPE — Eric Zimmerman's triage kit

KAPE (Kroll Artifact Parser and Extractor) separates what to gather from how to parse:

  • Targets — collection definitions (copy/compound sources from disk)
  • Modules — post-processing tools run against collected data

Suggested collection order (practical)

  • Document: hostname, time sync, who authorized collection, hash of images/exports
  • If memory in scope: capture RAM before heavy disk thrashing when possible
  • KAPE Targets for MFT + EVTX + Registry + Prefetch + Amcache on impacted Windows hosts
  • Run Modules; feed Hayabusa / timelines; escalate interesting hosts to full disk/memory
  • Velociraptor hunt across estate for the same IOCs discovered in triage

How do I prove X?

  • Program ran: Prefetch + Amcache + 4688/Sysmon 1 + UserAssist / Bam — prefer corroboration
  • File existed then deleted: MFT + USN Journal via MFTECmd workflow; $LogFile if available
  • Fleet still infected: Velociraptor hunt for hash/path/mutex; do not assume one host = all

Common exam traps

  • Confusing Target (collect) with Module (parse)
  • Skipping Prefetch on servers where Prefetch may be disabled — know the OS role
  • Collecting only Security.evtx and missing Sysmon / PowerShell / Task Scheduler logs
  • Forgetting chain of custody and hashing of collected archives
  • Running heavy Module parsing on the victim (prefer collect → analyze offline)

Lab takeaways

From Lab 2-1 — Triage collection
  • Order of volatility: capture memory before disk triage — RAM is lost on reboot.
  • Triage (SANS/KAPE-style targets) is faster than a full image and can keep a live DC in service; still hash and document custody.
  • Expect Registry hives + EVTX; note gaps (e.g. Users\Public staging may be omitted by the target set).
  • Dirty SOFTWARE hive: live copy → replay transaction logs = Yes; load dirty hive = Yes (Registry Explorer).
Quick reference
  • Velociraptor: collect | hunt | live response | artifacts
  • KAPE Target = collect (MFT, EVTX, Registry, Prefetch, Amcache)
  • KAPE Module = parse (MFTECmd, EvtxECmd, RECmd)
  • Order of volatility: memory → logs/registry → full disk
  • Triage = decide next steps, not write the full report yet

Mini self-check

Try answering without looking back. Expand each item for the answer.

Q1. Differentiate a KAPE Target from a KAPE Module with one example each.
A1. Target collects (e.g., Event Logs / MFT). Module parses (e.g., EvtxECmd / MFTECmd).
Q2. Name five high-value Windows collection areas commonly targeted by KAPE.
A2. MFT, Event Logs, Registry, Prefetch, Amcache.
Q3. Which Velociraptor capability finds a known malicious mutex across 500 hosts?
A3. Hunt (artifact/VQL hunt for that mutex).
Q4. Why parse EVTX offline with EvtxECmd after KAPE collection?
A4. Normalize and search at scale without altering the victim; faster multi-ID analysis; preserves originals.
Q5. What should you document before/during collection for court-ready work?
A5. Authorization, time/timezone, hostname, collector identity, tool versions, hashes of exports, chain of custody.
